# 长篇叙事知识与记忆工作流

用于完整小说、完整剧本、系列剧、多场景长片，以及任何要求跨章节、跨集或跨制作周期保持一致的项目。单个独立镜头不需要建立全书级图谱。

## 道：一部作品只能有一套可追溯事实

原始目标不是“积累更多文档”，而是让每个角色、场景、道具、事件、规则、视觉决定和已验收镜头都能回答：它是什么、来自哪里、当前哪个版本有效、改变后影响什么。原文证据与创作决定必须分开；候选、推断和共现不能伪装成正史。

## 法：四层知识与记忆协议

| 层 | 内容 | 真源与约束 |
|---|---|---|
| K0 原文证据 | 完整小说/剧本、稳定章节号、文件哈希、可靠范围 | 不可静默改写；哈希不一致停止构建 |
| K1 可检索知识 | 全文索引、实体规范名、别名、章节提及、证据片段 | 每条命中保留来源；短中文词可精确检索 |
| K2 关系与正史 | 人物、地点、道具、事件、规则、复现关系、资产版本 | 关系注明 `EXTRACTED / INFERRED / AMBIGUOUS`；候选经审阅才晋升 |
| K3 长期记忆 | 视觉宪法、批准决定、稳定约定、已知陷阱、失效理由 | 只保存未来会复用且不能从当前文件直接推导的信息 |

`project-state.json` 保存镜头运行状态，长期记忆保存稳定决定，两者不互相代替。进度和下一步属于项目状态，不重复写进长期记忆。

## 术：建立、查询、写回、失效循环

1. **建立**：先按 `source-ingestion-workflow.md` 固化完整来源与清单，再构建全文库、实体证据和关系图；初始化长期记忆。
2. **查询**：角色内核、三视图、场景、道具、座位、姿态、镜头和色调设计之前，先查规范实体、跨篇证据和既有决定。
3. **写回**：资产或视觉宪法通过人工门后，写回正史版本、来源、批准记录和下游依赖；镜头通过 QC 后只把观察到的首尾状态写入项目状态。
4. **失效**：原文、实体消歧、正史资产或视觉决定变化时，标记依赖项失效并重建受影响索引；不允许旧结果继续冒充当前事实。
5. **验证**：每次重建检查来源哈希、数据库完整性、可靠范围隔离、关键实体可查询和图谱邻域可遍历。

## 门禁：Knowledge Ready

同时满足以下条件才允许进入角色、场景、道具、导演本或分镜资产生成：

- 完整来源已登记；若版权或隐私限制存在，原文保持本地私有。
- 每个来源文件通过清单哈希校验，章节/场次有稳定 ID。
- 可靠范围已明确；隔离语料不会进入默认搜索、关系图或自动决策。
- 全文搜索能返回来源路径和证据片段；核心角色、复现地点和关键道具可按规范名查询。
- 知识图可从核心实体遍历到原文章节和已有设定，且不会把共现自动解释为人物关系。
- 长期记忆已初始化，并写入知识架构、可靠边界和连续性约定。
- 构建报告、SQLite `integrity_check` 和至少三个项目关键查询均通过。

知识底座未通过门禁时，不得进入角色、场景、道具或分镜资产生成。用户只要求局部试片时，仍先建立完整作品级知识底座，再把生成任务图限制在指定范围。

## 更新触发器

| 触发 | 必须写回 | 必须失效或重建 |
|---|---|---|
| 原文或剧本修订 | 新哈希、版本、变更范围 | 全文索引；受影响实体、事件和关系 |
| 实体消歧或别名确认 | 规范名、别名、证据、审阅者 | 旧候选边及引用旧 ID 的资产 |
| 角色/场景/道具资产获批 | 资产版本、锚点图、局部细节、来源和依赖 | 使用旧资产的未验收关键帧与镜头 |
| 视觉宪法或导演决定获批 | 决定、理由、适用范围、恢复点 | 冲突的场景规则和下游任务 |
| 镜头获批 | `observed_start`、`observed_end`、使用资产版本 | 后续从旧计划状态继承的镜头 |
| 用户纠正事实 | 纠正内容、原证据、最新决定 | 所有受影响推断；先查影响面再重跑 |

每次主要只改变一个事实或决定。写回后立即执行最小关键查询，证明新值可被检索、旧值不再作为当前正史返回。

## 器：本地调用合同

当前实现读取 `source/manifests/novel-manifest.json`，生成 `knowledge-base/knowledge.db` 与 `graphify-out/graph.json`、`graph.html`、`GRAPH_REPORT.md`：

```bash
python3 scripts/narrative_knowledge_base.py build <project> --reliable-end <N>
python3 scripts/narrative_knowledge_base.py search <project> <query> --limit 10
python3 scripts/narrative_knowledge_base.py entity <project> <canonical-name> --limit 100
python3 scripts/narrative_knowledge_base.py related <project> <query> --depth 1 --limit 100
```

构建还会生成 `knowledge-base/knowledge-ready-report.json`。它不是自述式完成标记，而是制片控制内核可复验的交付合同：报告绑定语料哈希、可靠范围及 `knowledge.db`、`graph.json`、`.agent-memory/meta/index.sqlite` 三份资产的内容哈希。`narrative_knowledge_foundation` 任务提交时，控制内核会逐章重验来源文件与清单哈希，证明数据库章节和全文索引确由当前来源重建，并复现实体提及；随后再执行 SQLite 完整性、可靠章节隔离、长期记忆结构检查，并要求图谱的节点集合和每条关系都能从数据库中的可靠章节证据或设定文档证据精确重建。任一项不符都拒绝进入视觉宪法与资产生产。

标准更新顺序为：固化来源版本 → 更新实体/别名与系列圣经 → 审阅长期记忆变更 → 重建记忆索引 → 重建知识库和图谱 → 提交 Knowledge Ready 报告 → 执行三个项目关键查询。批准资产或用户纠正触发同一循环，只重跑受影响的下游制作任务，但必须重新签发整部作品的底座报告。

不要直接依赖 Graphify CLI 查询两个汉字的人名或道具名；部分版本会丢弃长度不超过两个字符的词。使用上面的 `related` 适配层。

Codex 环境存在 `agent-memory` 时：

```bash
agent-memory init --name <project-name> --root <project>
agent-memory propose ...
agent-memory review --latest --diff
agent-memory apply --latest
agent-memory rebuild-index
agent-memory doctor
```

对 durable 决定和约定先暂存、查看差异再应用。没有 `agent-memory` 时，在项目内维护等价的可审阅决策与约定文件，仍要包含来源、状态、置信度和失效关系；不要把工具缺失当成跳过长期记忆的理由。

## 查询优先级

1. 用户最新明确决定。
2. 已批准视觉宪法、连续性合同和正史资产。
3. 可靠原文直接证据。
4. 已审阅推断。
5. 候选与歧义结果。

发生冲突时返回冲突和两边来源，不要静默选择。自动分镜只能使用前三层作为硬约束，后两层只能提示审阅。
