# 本地制片控制内核设计

## 目标与边界

### 道：本质目标

把 `cinematic-director` 从一次性提示词技能升级为可恢复、可审计、可逐级放权的制片管理底座。第一版由 Codex 领取任务包、调用合适的模型或工具并回填结果；控制内核只负责状态、依赖、版本、审批、追溯与交付，不把创作判断绑定到某一家模型。

### 硬约束

- 自动化必须分级，未验证的链路不得无人值守到底。
- 四个人工审批门不可绕过：视觉宪法、核心资产、样片镜头、画面锁定。
- 同一项目的创作事实、执行事实和媒体内容各有唯一真源。
- 所有任务输入、模型信息、提示词、种子、结果哈希和人工决定可追溯。
- 上游已接受版本变化时，下游受影响任务必须失效，不能静默沿用旧结果。
- 第一版不直接保存 API 密钥、不强依赖云服务、不把大媒体写入 Git。
- 任何项目都能在中断后恢复到最后一个已提交事务。

### 成功证据

1. 从项目清单可生成有向无环任务图，并停在第一个审批门。
2. 审批门前置条件不满足时，命令以非零退出码拒绝继续。
3. Codex 能领取一个机器可读任务包，提交候选结果，再由人工选择或退回。
4. 修改上游资产版本会递归标记依赖任务为 `stale`。
5. 运行中断后，过期租约能恢复为可重试状态，历史记录仍保留。
6. 最终导出包含成片清单、素材血缘、审批记录和连续性状态摘要。

## 已选架构

采用“本地优先制片控制内核”：Python 标准库提供命令接口，SQLite 保存执行账本，文件系统保存输入、媒体与导出物，供应商适配层只定义任务包和结果回填合同。

参考同类项目时只吸收可验证的机制：OpenCode 的模型中立任务调用，Huobao Drama 的角色/场景/道具/分镜领域拆分，Waoowaoo 的运行事件与租约恢复，`ai-video-pipeline` 的清单和参考图传递，KupkaProd 的多候选 take 选择。未声明许可证或非商业许可证项目不复制代码。

## 道→法→术→器

### 法：稳定协议

```text
项目输入
  -> 制片计划与任务图
  -> 视觉宪法审批门 G1
  -> 角色/场景/关键道具资产审批门 G2
  -> 分镜与样片审批门 G3
  -> 全量镜头、声音、粗剪
  -> 画面锁定审批门 G4
  -> 最终导出
```

任务只能在依赖完成且所需审批门已通过时进入 `ready`。执行器领取任务时获得固定输入快照；提交结果时内核重新核对输入哈希，防止用过期上下文写回。

### 术：分级自动化

- `guided`：默认级别。Codex 每次领取一个任务包，人工处理所有审批门。
- `batch-within-gate`：已证明稳定后，可在同一审批门区间自动执行一批任务；到门即停。
- `supervised-run`：未来允许带预算、失败阈值和供应商策略的长运行，但仍保留四个门。
- `unattended`：不在第一版范围内；只有真实项目证据满足成功率、成本和回滚指标后才讨论。

### 器：实现选择

- Python 3 标准库：命令、领域规则、JSON 校验。
- SQLite：事务、事件账本、任务与版本索引。
- 文件系统：项目输入、媒体文件、内容寻址对象和交付物。
- `unittest`：公共行为和故障恢复测试。

## 领域模型

```text
Project
  -> Sequence -> Scene -> Shot
  -> Asset -> AssetVersion
  -> Task -> Run -> Candidate -> Review
  -> GateDecision
  -> Deliverable
  -> Event
```

- `Task`：一个可领取的工作单元，记录阶段、依赖、所需审批门、输入引用和状态。
- `Run`：一次执行尝试，记录执行器、租约、请求快照、完成或失败信息。
- `Candidate`：一次运行产生的候选，可有多个；只有被选择的候选才能成为接受版本。
- `AssetVersion`：不可变资产版本，内容或元数据变化必须创建新版本。
- `Review`：对候选、资产或镜头的通过、拒绝、修改要求。
- `Event`：每次状态变化的追加式审计记录。

## 三个唯一真源

### 执行账本

项目目录下 `.production/production.db` 保存任务状态、运行、租约、候选、版本血缘、审批门和事件。派生状态可重建，事件不得原地改写。

### 创作连续性

`project-state.json` 继续作为人物、场景、道具、视觉宪法和镜头观察状态的唯一机器真相。控制内核只登记它的版本与哈希，不复制其中的创作字段。

### 媒体内容

媒体保存在 `media/objects/<sha256-prefix>/<sha256>`，数据库只登记内容哈希、原始名称、媒体类型和逻辑用途。相同内容去重，大文件不进入 Git。

## 任务状态机

```text
planned -> blocked -> ready -> leased -> submitted -> accepted -> completed
                                  |          |            |
                                  v          v            v
                               failed     rejected       stale
```

- `planned/blocked`：依赖或审批门未满足。
- `ready`：允许执行器领取。
- `leased`：某次运行已领取并带过期时间。
- `submitted`：已有候选，等待选择或评审。
- `accepted/completed`：候选已选择，任务完成。
- `failed/rejected`：可保留历史并创建下一次运行。
- `stale`：上游输入版本改变，必须重算或人工明确豁免。

## 四个审批门

| 审批门 | 必须存在的证据 | 通过后解锁 |
|---|---|---|
| `visual_constitution` | 项目视觉宪法、视觉弧、破例预算 | 角色/场景/道具资产生产 |
| `core_assets` | 主要角色三视图与细节、核心场景多视图、关键道具版本 | 分镜与样片生产 |
| `pilot_shots` | 代表性样片、连续性检查、成本与模型可行性记录 | 全量镜头、声音与粗剪 |
| `picture_lock` | 粗剪清单、未决问题为零、镜头版本锁定 | 最终合成与交付导出 |

审批是带证据哈希的不可变决定。上游批准对象变化后，相关审批门变为 `invalidated`，下游任务同步失效。

## Codex 执行合同

第一版不要求内核直接连接模型 API。Codex 通过稳定命令完成闭环：

1. `init`：初始化项目与数据库。
2. `ingest`：登记剧情、剧本、视觉参考和已有资产。
3. `plan`：导入由导演技能编译的结构化制片计划。
4. `next`：领取一个任务包，包含目标、输入版本、视觉约束、输出合同和租约。
5. Codex 根据任务能力选择图像、视频、音频或文本模型。
6. `submit`：登记候选文件、模型、提示词、种子和元数据。
7. `review`：选择候选、退回或要求重试。
8. `approve-gate`：人工确认审批门；内核验证前置证据。
9. `status/recover/export`：查看进度、恢复过期运行、导出交付清单。

所有命令默认输出 JSON，业务拒绝返回非零退出码，便于 Codex 确定下一步。

## 计划输入合同

`production-plan.json` 至少包含：

- 项目标识、标题和输入文件引用。
- 视觉宪法状态文件引用。
- 角色、场景、道具、序列、场景和镜头的稳定 ID。
- 每个任务的 `id`、`kind`、`stage`、`depends_on`、`required_gate`、`inputs`、`output_contract`。
- 每个审批门的证据任务列表。

内核校验 ID 唯一、引用存在、任务图无环、审批门顺序合法、输出合同完整。导演技能负责从剧情生成这些创作内容，内核不重复进行语言模型推理。

## 一致性与失效传播

- 每次领取任务时计算输入快照哈希，包含依赖任务的接受候选、引用资产版本和 `project-state.json` 哈希。
- 提交时输入哈希不匹配则拒绝候选，运行标记为 `stale_input`。
- 接受新的上游候选后，按任务图递归将已完成下游标记为 `stale`。
- 项目级视觉宪法默认继承到序列、场景和镜头；局部覆盖必须记录原因、范围与恢复点。
- 只有已接受镜头能把 `observed_end` 回写为后继镜头的真实起点。

## 恢复、并发与回滚

- SQLite 使用外键、事务和 WAL；每次状态变化与事件追加在同一事务完成。
- 任务领取产生租约。租约过期后 `recover` 把运行标记为 `interrupted`，任务恢复为 `ready`。
- 接受版本不可覆盖；回滚是重新指向旧版本并产生新事件，不删除历史。
- 第一版默认单执行器，但用原子条件更新防止两个执行器同时领取同一任务。

## 安全与成本边界

- 数据库不保存 API 密钥；执行器从自己的受控环境读取凭据。
- 文件导入使用内容复制，不执行输入文件。
- 路径必须限制在项目目录内，拒绝目录穿越和符号链接逃逸。
- 第一版只记录估算与实际成本，不自动发起付费调用；是否调用模型由 Codex 当前权限和用户策略决定。
- 导出前验证所有审批门、无 `stale` 任务、无过期运行和无未决拒绝。

## 非目标

- 第一版不提供 Web UI、多人权限系统或远程队列。
- 第一版不承诺直接适配所有图像/视频/声音供应商。
- 不自动决定不可逆的视觉宪法、核心资产、样片或成片定版。
- 不把 SQLite 当媒体仓库，也不把模型输出存在 Git 历史中。

## 后续 B 阶段兼容性

未来 Web 制片台只通过同一领域服务和数据库合同提供项目看板、资产版本对比、候选审片、成本监控与审批操作。CLI 是第一客户端，不是一次性脚本；B 阶段不得另建一套状态机。
